# Booking Alarm System — Complete Documentation
    
## Overview

Persistent booking notification alarm for the Plate ecosystem. When a new booking arrives and remains unattended (pending), an alarm sound loops continuously until the restaurant staff accepts or declines it. This is a critical feature used by all restaurant merchant apps (Uber Eats, DoorDash, Toters, TheFork, etc.).
      
Implemented across two platforms:
1. **Plate Merchant** — React Native Expo app (Samsung tablets)
2. **RBS Restaurant** — Next.js PWA (web dashboard)
      
---

## Platform 1: Plate Merchant (React Native / Android)

### Architecture

Native Android foreground service (`BookingAlarmService.kt`) with `MediaPlayer` for reliable, persistent alarm sound that survives app backgrounding, screen off, and task swiping.

```
New Booking Arrives
    ├─ FCM background handler → startBookingAlarm()
    ├─ Supabase Realtime INSERT → displayNewBookingNotification() → startBookingAlarm()
    ├─ Supabase polling (15s) → displayNewBookingNotification() → startBookingAlarm()
    └─ Initial load effect → displayNewBookingNotification() → startBookingAlarm()
            │
            ▼
    BookingAlarmModule (JS bridge)
            │
            ▼
    BookingAlarmService.kt (native foreground service)
        ├─ MediaPlayer.create(context, R.raw.new_booking, attrs, sessionId)
        ├─ isLooping = true
        ├─ Foreground notification ("New Booking Alert")
        └─ PARTIAL_WAKE_LOCK
            │
            ▼
    Sound loops until ALL pending bookings are resolved
```

### Key Bugs Fixed

1. **`require('expo-notifications').default` → `undefined`** in FCM background handler — silently broke all background notifications
2. **Notification identifier mismatch** — `booking-` vs `booking_` prefix meant dismiss calls never worked
3. **`ensureSoundPlaying` didn't exist** — imported but never defined, would crash on app resume
4. **`setAudioAttributes` after `MediaPlayer.create()`** — called after `prepare()`, silently routed audio to nowhere
5. **Effect snapshot condition swallowed first booking** — `previousPendingIdsRef.current.size === 0 && currentPendingIds.size > 0` treated the first new booking as an initial snapshot
6. **EAS Build wiped native files** — `expo prebuild` regenerated `MainApplication.kt` and `AndroidManifest.xml`, losing manual changes. Fixed with config plugin that generates everything.

### Defense-in-Depth Layers

| Layer | What | When |
|---|---|---|
| 1. Screen stays on | `expo-keep-awake` / `useKeepAwake()` | Prevents Doze entirely while app is open |
| 2. Foreground service (listening) | Native service started at login | Keeps process alive, holds wake lock |
| 3. Supabase Realtime | INSERT events in `booking-status-monitor.ts` | Instant detection while JS is active |
| 4. JS polling (15s) | `setInterval` in `booking-status-monitor.ts` | Catches missed Realtime events |
| 5. FCM background | `setBackgroundMessageHandler` starts native alarm | Works during Doze maintenance windows |
| 6. Native alarm service | `MediaPlayer` in foreground service | Survives backgrounding, screen off, task swipe |

### Samsung Tablet Setup Required

After installing the app:
1. Accept the battery optimization exemption prompt
2. Settings > Battery > Background usage limits > **Never sleeping apps** > Add Plate Merchant
3. Disable "Put unused apps to sleep"
4. Keep the tablet plugged in during service hours

## Platform 2: RBS Restaurant (Next.js PWA)

### Architecture

Browser-based `<audio loop>` with Screen Wake Lock API. Works when the PWA tab is in the foreground (same requirement as Uber Eats web dashboard).

```
New Booking Arrives
    ├─ Supabase Realtime INSERT → addNotification() → bookingAlarmService.startAlarm()
    ├─ Service Worker push → PLAY_ALARM broadcast → bookingAlarmService.startAlarm()
    └─ Initial page load → checks existing pending → bookingAlarmService.startAlarm()
            │
            ▼
    bookingAlarmService (singleton)
        ├─ new Audio('/sounds/booking-notification.mp3')
        ├─ audio.loop = true
        ├─ navigator.wakeLock.request('screen')
        └─ Autoplay unlock on first user click/tap
            │
            ▼
    Sound loops until ALL pending bookings are resolved
```

### Key Discovery: Dead Code

`GlobalLayoutNotifications` (the component that runs the global Supabase Realtime subscription for booking sounds) was **defined but never mounted** in the layout tree. The Realtime subscription was dead code. Fixed by adding it to the dashboard layout.

### Browser Limitations vs Native

| Scenario | Native (Plate Merchant) | PWA (RBS Restaurant) |
|---|---|---|
| Tab/app in foreground, screen on | Alarm loops | Alarm loops |
| Screen auto-turns-off | `useKeepAwake` prevents it | Screen Wake Lock prevents it |
| User manually locks screen | Foreground service keeps alarm | Audio stops (browser suspended) |
| User switches app/tab | Foreground service keeps alarm | Audio stops (tab backgrounded) |
| App/tab closed | Foreground service survives (START_STICKY) | Everything stops |
| Push notification in background | FCM starts native alarm service | Shows notification with one-time sound |
| Autoplay restriction | None (native audio) | First click/tap required to unlock audio |

### Browser Autoplay Policy

Browsers require at least one user interaction (click, tap) before `audio.play()` works. The implementation handles this by:
1. Listening for the first `click` or `touchstart` event on the document
2. Playing a silent audio snippet to unlock the audio context
3. If pending bookings exist when audio is unlocked, the alarm starts immediately

## Maintenance Notes

- **Plate Merchant Kotlin code lives in the config plugin** (`plugins/withBookingAlarm.js`), NOT in the `android/` directory directly. The plugin generates the Kotlin files during `expo prebuild` / EAS Build. To modify the native service, edit the template strings in the plugin.
- **Sound files** should be kept in sync between platforms if the alarm sound is changed.
- **The `cancelBookingNotification()` function** in `booking-notification-service.ts` is the single teardown entry point for the native app. It handles: alarm stop + notification dismiss + polling interval cleanup. Don't call individual stop functions separately.
- **The `bookingAlarmService` singleton** in the PWA is the single point of control. `startAlarm(id)` and `stopAlarm(id)` are idempotent — safe to call multiple times for the same booking.
